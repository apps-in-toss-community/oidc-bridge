## 1. CI debugging cycle 1: better-sqlite3 native binding

### Symptom

After 19 tasks all green locally, the CI build job for the `zero-code-mode` PR failed at `pnpm test`:

```
Could not locate the bindings file. Tried:
  → /home/runner/work/.../node_modules/better-sqlite3/build/Release/better_sqlite3.node
  → /home/runner/work/.../node_modules/better-sqlite3/lib/binding/node-v137-linux-x64/better_sqlite3.node
  ...
```

### Why local passed but CI failed

macOS workstation: `better-sqlite3` shipped a `darwin-arm64` prebuilt binary, so `pnpm install` placed it under `lib/binding/...` and the require resolved.

Linux x64 CI: no matching prebuilt for the runner's combination, so the install would normally trigger a `node-gyp rebuild`. **But pnpm 10's default install policy blocks `install`/`postinstall`/`preinstall` scripts of dependencies for security.** No rebuild ran, so the binding never landed.

### Why we didn't catch this in M0

M0 used `pnpm@9.x` which still ran build scripts by default. The repo bumped to pnpm 10.33.0 in the `chore: standardize pre-commit hook, biome config, and CI lint (#5)` commit, before any native dependency was added. Phase 1 was the first feature to introduce one (better-sqlite3), so it was the first time the policy mattered.

### Decision: explicit allowlist in `package.json`

```json
"pnpm": {
  "onlyBuiltDependencies": [
    "better-sqlite3"
  ]
}
```

Committed as `dc69123 fix(ci): allow better-sqlite3 build script via pnpm.onlyBuiltDependencies`.

**Rejected alternative: `pnpm approve-builds`.** Approve-builds is an interactive permission grant for *running* the script. The toolchain to *execute* the script (python3/make/g++) is a separate axis. On the CI Ubuntu runner the toolchain happened to exist, so approve-builds would also have worked there — but the Docker alpine image has no toolchain at all, and approve-builds wouldn't help that case. The static `onlyBuiltDependencies` allowlist is also reproducible across machines (CI, fresh clones, Codespaces) without an interactive step.

### Future signal

When adding a native module:
1. Add it to `pnpm.onlyBuiltDependencies` in the same PR.
2. Verify CI's runner OS has matching prebuilt OR the Docker builder has the toolchain (see story 2).
3. If you bump pnpm major in a chore PR, sweep existing dependencies for `install`/`postinstall` hooks — they'll silently no-op.

## 2. CI debugging cycle 2: Docker alpine builder missing Python

### Symptom

After fix 1 landed, the **CI test job** turned green. The **`docker-build` job** then failed during `pnpm install` in the builder stage:

```
gyp ERR! find Python
gyp ERR! command "node" "/app/node_modules/.pnpm/node-gyp@.../bin/node-gyp.js" "rebuild"
```

### Why

`Dockerfile` builder is `node:24-alpine`. Alpine uses **musl libc**, and `better-sqlite3` does not ship a musl prebuild. With fix 1, pnpm now correctly *attempts* the install script, which falls back to `node-gyp rebuild`. node-gyp needs python3/make/g++, none of which alpine includes.

### User-facing tradeoff

The user explicitly chose to keep the runtime image alpine for size reasons rather than switching to debian/distroless. The acceptable cost is heavier builder, slim runtime.

### Decision: builder-only toolchain

Added to the **builder stage only**:

```dockerfile
FROM node:24-alpine AS builder
...
# better-sqlite3 ships no musl prebuild, so the install script falls back to
# `node-gyp rebuild`. python3/make/g++ are needed for that compile only; the
# runtime image keeps alpine's lean footprint.
RUN apk add --no-cache python3 make g++
```

Runtime stage stays `node:24-alpine` with `--from=builder /app/node_modules` copied in. Final image size unchanged (the apk packages don't get into the runtime layer).

Committed as `b5a08e2 fix(docker): install python3/make/g++ in builder for better-sqlite3 musl compile`.

### Future signal

When adding a native module that doesn't ship musl prebuilds:
- Builder stage may need `python3 make g++` (already there, no-op).
- If we ever pick up a native dep that needs other toolchain (e.g. `libffi-dev`, `openssl-dev`), add to that same `apk add` line. Group the rationale comment so the next reader knows why.

Alternative we did NOT take: switching to `node:24-slim` (debian) for both stages. That would skip the toolchain dance and we'd get glibc prebuilds for free, but the runtime image would grow from ~150MB to ~250MB. The user values size for the public Cloud Run instance.

## 3. ORM choice survives scrutiny

The user asked twice during Phase 1 whether `better-sqlite3` is really necessary "since we have an ORM." Two facts that ended up in CLAUDE.md but are worth restating:

1. **Drizzle is driver-agnostic.** It compiles queries; it does not implement them. `drizzle-orm/better-sqlite3` is a thin adapter that takes a driver instance. *Some* native sqlite binding is required.
2. **Performance is fine for our workload.** Bridge requests are sub-ms with ≤2-3 queries each. better-sqlite3's sync API + native binding is the fastest sqlite path in Node, and the sync API is fine here because we never block long.

**Alternatives considered and rejected for now:**

| Driver | Why not (now) |
|---|---|
| `@libsql/client` | Async-only, broader feature set we don't need (replication, Turso). Adds a layer with no win. |
| `node:sqlite` (Node 24+) | Experimental flag in Node 24. Promotion timeline unclear. Worth re-evaluating in Phase 9 (self-host artifacts) — it would *eliminate* the alpine-builder toolchain story if mature by then. |

Phase 9 reminder: re-check `node:sqlite` stability before publishing the self-host Docker image as v1. If it's stable + supports our schema, we can drop better-sqlite3 + the apk add line + onlyBuiltDependencies entry.

## 4. Drizzle 0.45.2 footguns we hit

These are codified in CLAUDE.md "Standing decisions"; here is the *evidence*.

### `bytea` customType not exported

We needed `bytea` for `apps.mtls_cert_sealed` / `mtls_key_sealed`. Drizzle 0.45.2's `pg-core` exposes JSON, text, varchar, etc. but not bytea as a top-level helper. Found in `node_modules/drizzle-orm/pg-core/columns/index.d.ts`. Defined our own via `customType<{ data: Buffer; driverData: Buffer }>` with `dataType: () => 'bytea'`.

If drizzle-orm 0.46+ adds bytea, swap.

### `$onUpdateFn` is required, not optional

A column with only `.defaultNow()` will set `created_at = now()` on insert but **will not refresh** on update. We discovered this when a conformance test set timestamps via UPDATE and the column stayed at the original insert time. Pattern for `updated_at`:

```ts
updatedAt: timestamp('updated_at', { withTimezone: true })
  .notNull()
  .defaultNow()
  .$onUpdateFn(() => new Date()),
```

Both `defaultNow()` (for INSERT) and `$onUpdateFn` (for UPDATE) are needed. Same pattern in sqlite mirror with `sql\`(unixepoch())\`` defaults.

### SQLite expression index DESC: reviewer was wrong

The code-quality reviewer subagent claimed a SQLite expression index using DESC ordering wouldn't work and asked us to remove the DESC. Empirical check:

```sql
CREATE INDEX idx_audit_app_created ON audit_log (app_id, created_at DESC);
```

works in SQLite ≥3.3.0 (2006). Our better-sqlite3 ships SQLite 3.45+. Test passed; we kept DESC and moved on.

**Lesson:** subagent reviewers (especially smaller models) sometimes assert false constraints. When a claim is testable in <30 seconds, test it; do not capitulate.

### `OWNERSHIP_STATUSES` runtime guard

Drizzle pgTable supports `text(...).$type<UnionType>()` for compile-time narrowing but does not generate a DB-level `CHECK`. We added a runtime guard:

```ts
const OWNERSHIP_STATUSES = new Set(['α', 'verified', 'lapsed', ...] as const);
function assertOwnershipStatus(s: string): asserts s is OwnershipStatus {
  if (!OWNERSHIP_STATUSES.has(s)) throw new Error(`bad ownership status: ${s}`);
}
```

Phase 2 will exercise this when admin endpoints write the column.

### Empty patch in `updateWorkspace`

Drizzle's `db.update(...).set(values)` throws "No values to set" if `values` is `{}`. Our partial-patch helper accepted `{}` to mean "no change," which is a reasonable API. Wrapped:

```ts
async function updateWorkspace(id, patch: Partial<WorkspaceRow>) {
  if (Object.keys(patch).length === 0) return;
  await db.update(workspaces).set(patch).where(eq(workspaces.id, id));
}
```

Phase 2 admin handlers will reuse this guard pattern.

## 5. Vitest 4 config gotcha

Vitest 4 removed `test.poolOptions.pool` and replaced it with **top-level** `pool: 'forks'`. We needed forks (not threads) because pg conformance tests open real Pool connections to a health-checked Postgres service, and threaded test isolation interacts badly with libpq's `unref` semantics on cleanup.

Final `vitest.config.ts`:

```ts
import { defineConfig } from 'vitest/config';
export default defineConfig({
  test: {
    pool: 'forks',
    poolOptions: { forks: { isolate: true } },
  },
});
```

If a future phase adds heavy-parallelism unit tests and wants to *opt out* of forks, do it per-file with the `// @vitest-environment` style hint, not by reverting the global.

## 6. Storage conformance pattern

`runStorageConformance(name, factory)` is the single test file shape for both pg and sqlite. PG is gated:

```ts
const url = process.env.PG_TEST_URL;
if (!url) {
  describe.skip('Storage conformance — pg (PG_TEST_URL not set)', () => {});
} else {
  runStorageConformance('pg', { open, cleanup });
}
```

CI sets `PG_TEST_URL` job-wide and runs `postgres:16-alpine` as a service container with health check. Local dev runs without it; sqlite always runs.

Inside `open()` we run drizzle migrations idempotently, then TRUNCATE all tables with `RESTART IDENTITY CASCADE`. Dropping the database between tests was rejected (slow) — TRUNCATE-then-migrate is fine because migrations are idempotent.

When Phase 2 introduces new tables, they get added to:
1. Both `schema.pg.ts` and `schema.sqlite.ts` (hand-mirrored).
2. The TRUNCATE list in `pg.test.ts` (and sqlite equivalent) — tables not in the list will accumulate state across test files.
3. New conformance test cases under `runStorageConformance`.

## 7. Subagent workflow lessons

We ran 19 tasks via `superpowers:subagent-driven-development` with implementer + spec-reviewer + code-quality-reviewer subagents per task.

### What worked

- **Fresh context per task** kept implementations focused. The implementer subagent for "HKDF derivation" had no idea what the master-key cache looked like, which is fine because that boundary is exactly the file boundary.
- **Two-stage review** caught real spec gaps (e.g. one task implemented HKDF without the `appId` empty-check the spec required). Spec compliance review > code quality review ordering matters; code quality review on a spec-non-compliant impl is wasted.
- **Verbatim task text** in dispatch prompts: copy/paste the plan task into the prompt, do not summarize. Saves the implementer from re-reading the plan and prevents drift.

### What needed adjustment

- **Default `Agent` model is opus** (inherited from parent). Mirror tasks (PG driver = structural mirror of SQLite driver) ran on opus and burned cost. Pattern going forward: explicit `model: 'haiku'` for true mirror tasks, `'sonnet'` for general implementation, `'opus'` only for genuinely novel design.
- **Reviewer false confidence** (see story 4, SQLite DESC). Treat reviewer subagent claims as hypotheses to verify, not facts. The `BLOCKED`/`DONE_WITH_CONCERNS` channel is the right place for the reviewer to flag uncertainty; if they don't, we still verify load-bearing assertions.
- **Skipping quality review on mirror tasks** is fine. Both subagents on the same structural-mirror file is wasted spend; spec compliance review is enough.

## 9. Carryover for Phase 2

Things Phase 2 should keep in mind based on Phase 1:

1. **bcrypt rotation overlap**: store an array of valid hashes per `api_token`, not a single hash. Phase 1 mTLS sealing already established the column shape (`bytea` per `apps.mtls_cert_sealed`); Phase 2's bcrypt array uses a similar JSON-of-hashes-or-text-array shape — pick one and lock it.
2. **mTLS column write path** lives in `apps/`, not `oidc/`. The seal/unseal helpers from `master-keys/` and `oidc/sealed-token.ts` are both per-app HKDF-keyed but **different `info` strings**: `ait/seal/v1` for tokens, pick a distinct `info` (e.g. `ait/mtls/v1`) for mTLS column wrap so a token-cipher leak can't decrypt mTLS material.
3. **Admin REST shape** must keep mTLS material out of GET responses (`***` mask) — universal invariant #8 from the index.
4. **Audit log writer** runs after every state-changing admin operation. `audit/log.ts` is its own module so route handlers stay thin.
5. **Ownership state machine** lives in `apps/ownership.ts`. The transitions (`α → verified | lapsed`, `lapsed → reassign`) are spec §6.7. Use the runtime guard pattern from story 4.

If anything in the standing-decisions list of CLAUDE.md becomes obsolete after Phase 2 (e.g. better-sqlite3 dropped for `node:sqlite`, or pnpm 11 changes the policy), update CLAUDE.md *and* add a Phase 2 retro file to record what changed. Don't silently overwrite this file — it's history.
