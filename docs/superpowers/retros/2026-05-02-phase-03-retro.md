## 1. Plan-vs-shipping audit moved upstream

### What happened

The Phase 3 plan was authored *before* Phase 2 was implemented, against a design-doc-only mental model of what Phase 2 would look like. By the time PR #21 (Phase 2 (2/2)) merged, the Phase 3 plan had four blockers that would have crashed the worker mid-execution:

1. `'active'` ownership status (didn't exist; actual is `'pending' | 'verified' | 'lapsed'`)
2. HKDF import path `'../crypto/hkdf.js'` (didn't exist; actual is `'../master-keys/index.js'`)
3. `service.apps.getByClientId(...)` (didn't exist; actual is `storage.getAppByClientId(...)` — the service layer was bypassed)
4. `service.audit.append({actor: {type, id}, ...})` with a structured actor (didn't exist; actual is `appendAudit({storage, actor: string, ...})` with a plain-string actor and storage handle passed explicitly)

Items 1 and 2 were surgical search-and-replace and were patched directly in the plan file in PR #22. Items 3 and 4 were too invasive for safe mass-edit so they were captured as deviation instructions in `docs/superpowers/plans/2026-05-01-zero-code-phase-03-amendments.md`. The plan header banner points worker subagents at the amendments doc.

### Decision: re-audit at predecessor merge, not successor start

The audit ran on the same day Phase 2 merged. If we had waited for Phase 3 to start, the worker would have hit each blocker individually, with stale plan code already committed. Pattern going forward:

> Plans authored ahead of the predecessor phase's implementation are re-audited at the moment the predecessor merges, not at the moment the successor starts.

Codified as a checkpoint in the index doc.

### Future signal

When merging a phase that ships a new public surface (`Service`, `Storage`, audit writer, error types, …), grep the next phase's plan for symbols and types and reconcile *before* the next worker subagent starts.

## 2. AAD-circular-dependency in sealed-token format

### Symptom (anticipated, not hit at runtime)

Spec §12 decision 17 specified the AAD as `app_id || toss_user_key || sealing_key_version`. But unwrap can't *know* `toss_user_key` until after decryption — it's not in the wire format. The original wire format `version || iv || ciphertext || tag` had no place to put it. Without resolution, every unwrap would have failed AEAD verification.

### Resolution: extend wire format to embed `userKey`

Final wire format: `version || userKey_len || userKey || iv || ciphertext || tag`. `userKey` is read off the wire as plaintext and bound into AAD. Plaintext-leaked? Yes, but `userKey` is not a secret (it's already in the id_token claims and `/oidc/userinfo` response). The trade is "bind to userKey at verification time" vs "rotate userKey to break old tokens" — we keep verification.

Helpers `peekSealedTokenVersion` and `peekSealedTokenUserKey` read the prefix bytes without unwrapping, which Phase 4 (userinfo / revoke / raw-tokens) needs to do app lookup *before* deciding on sealing key version.

Tests in `src/oidc/sealed-token.test.ts` lock:
- Roundtrip on the same `(appId, userKey, version)` succeeds
- Tamper on the ciphertext or tag fails
- Cross-version replay (same payload sealed with v2 keys, presented with v1 prefix) fails
- Cross-app replay (same payload sealed with app A's key, presented with app B's id) fails

### Future signal

If Phase 4 or later wants to add another field to the AAD (e.g. `client_id`, `aud`), it has to either be in the request context (header, body) or in the wire prefix. Don't pile fields into the wire prefix without re-justifying the plaintext leak.

## 3. MockTossAdapter as the Phase 3–4 contract surface

### What worked

`TossAdapter` interface (`src/toss/adapter.ts`) plus `MockTossAdapter` (`src/toss/mock-adapter.ts`) let Phase 3 fully exercise the token endpoint without any network. The mock returns deterministic `accessToken`/`refreshToken`/`expiresIn` keyed by the input `authorizationCode`, and counters expose call assertions to tests.

Redacted SUCCESS/FAIL fixtures live under `src/toss/fixtures/` (`generate-token-success.json`, `generate-token-fail.json`, `login-me-success.json`, `refresh-token-success.json`). They were transcribed from sandbox captures with PII fields redacted. Phase 5 will replace `MockTossAdapter` with a real mTLS adapter against the same fixtures-derived contract; until then, every consumer (`tokenService`, `userinfo` in Phase 4, `revoke` in Phase 4) goes through the adapter interface, never raw `undici`.

### Carryover for Phase 4

`MockTossAdapter` needs `accessRemove(refreshToken)` for Phase 4's revoke route. Plan Task 8 already specifies this — use the same counter pattern. Don't add real network in Phase 4; that's strictly Phase 5.

## 4. RSA signing key registry + multi-kid JWKS

### Decision

`OIDC_SIGNING_KEY_<KID>_PEM` env vars (one per kid) plus `OIDC_ACTIVE_KID` to pick the signing one. JWKS publishes *all* configured kids so verifiers tolerate rotation overlap. The plan originally specified a single `OIDC_SIGNING_KEY` env (M1 shape); we changed it to multi-kid to match spec §5.6 and Phase 1's master-key rotation pattern.

### Footnote that bit us in PR #25

The Phase 3 PR shipped multi-kid envs but `.github/workflows/deploy.yml` and `.env.example` still referenced the single-key M1 envs. Deploy on main failed fast because the workflow required `TOSS_CLIENT_ID` + `TOSS_CLIENT_SECRET` (M1 single-tenant Basic Auth, structurally incompatible with zero-code mode where credentials are per-app and DB-resident). PR #25 swept `.env.example` + `deploy.yml` + `docs/DEPLOY.md` in lockstep to drop the M1 envs and add the OIDC signing trio. No code changed; pipeline is now green.

### Lesson

When a phase changes config surface (new envs, removed envs), grep the deploy workflow and operator docs in the same PR. Phase 3 did not — it only edited `.env.example` for the *new* envs, leaving the *removed* envs in deploy.yml. Phase 4 has no env churn planned, but Phase 5 (real Toss mTLS) and Phase 8 (rate-limit + observability) will — apply this sweep then.

## 6. What would have been Phase 2 retro

No standalone Phase 2 retro file exists. The Phase 2 lessons that *would* have gone here were captured by PR #22 instead:

- **Plan-vs-shipping audit pattern** (this retro §1) is the load-bearing Phase 2 lesson; PR #22 amendments doc embodies it.
- **Service / Storage layering decision** — Phase 2 ended up with a thin `Service` (admin REST handlers) on top of `Storage` (DB primitives). Read paths bypass the service layer (token route uses `storage.getAppByClientId` directly). Write paths through admin REST go through `Service` for invariants like ownership state machine + audit logging.
- **bcrypt rotation overlap** — `apps.client_secret_hashes: text[]` (PG) / JSON-array (SQLite). Multiple hashes valid concurrently for rotation. `verifyClientSecret(plain, hashes[])` returns true on any match. Phase 4 confidential-client auth depends on this.
- **mTLS column sealing** — `apps.mtls_cert_sealed` / `mtls_key_sealed` use `info: 'ait/mtls/v1'`, distinct from `info: 'ait/seal/v1'` for tokens. A token-cipher leak can't decrypt mTLS material.
- **Ownership state machine** — `apps.ownershipStatus: 'pending' | 'verified' | 'lapsed'`. Phase 3 token route gates on `=== 'verified'` (not a superseded `'active'` literal — see §1).

Keep the policy: "1 retro per phase, exception only when the lessons are already written down somewhere durable." PR #22 is durable.

## 7. Carryover for Phase 4

Things Phase 4 should keep in mind based on Phase 3:

1. **Reuse `peekSealedTokenVersion` + `peekSealedTokenUserKey`** for app/key lookup in `userinfo` and `revoke` — don't re-implement prefix parsing.
2. **`Storage.getAppByClientId` not `Service`** — same pattern as token route. Confidential auth's `verifyClientSecret(plain, app.clientSecretHashes)` reuses Phase 2's helper.
3. **`appendAudit({storage, actor, action, target, details?})`** — extend `AuditAction` with `'oidc.userinfo.read'`, `'oidc.token.revoke'`, `'oidc.raw_tokens.read'` in the first task that needs auditing.
4. **`Authorization` header + `token` form field redaction** — Phase 0 redact list covers `client_secret`, `refresh_token`, `code`, `access_token`, `id_token`, `code_verifier`, `mtls_*`. Phase 4 plan Task 17 verifies (does not extend) — the existing list already covers the new fields by name, but confirm in test before merging.
5. **In-memory `RevocationStore`** — per-instance is fine per spec §9. Don't reach for Redis; Phase 8's rate-limit decision will revisit this if multi-instance becomes load-bearing.
6. **`MockTossAdapter.accessRemove(refreshToken)`** — counter pattern, no real network. Phase 5 swaps in the real adapter against the same interface.
7. **Confidential-client `client_secret_basic` + `client_secret_post`** — Phase 2 ships `verifyClientSecret(plain, hashes[])` with rotation overlap. Lock down "mixing public Origin + confidential `client_secret` on the same call → reject" with explicit tests (plan Task 12). The lesson from M1 was that auth-method ambiguity is exploitable.
8. **Origin enforcement hardening** — Phase 3 accepts a missing `Origin` header on confidential calls (which is fine — confidential clients aren't browser-driven). Phase 4 must reject *malformed* Origin (e.g. a string that's not a URL) on public calls instead of silently allowing through. Plan Task 11.

If anything in CLAUDE.md "Standing decisions" or this retro becomes obsolete after Phase 4 (e.g. revocation moves out of memory, `MockTossAdapter` is retired), update CLAUDE.md *and* add a Phase 4 retro file. Don't silently overwrite this file — it's history.
