## 1. Sealed-token preamble grew an `appId` hint

### What happened

Phase 3 closed §2 ("AAD-circular-dependency in sealed-token format") by binding `userKey` into the wire preamble so unwrap could rebuild AAD. Phase 4's three new endpoints (`/oidc/userinfo`, `/oidc/revoke`, `/oidc/raw-tokens`) are **body-less** — they receive a sealed `ait_*` bearer or form `token` and need to look up the owning app *before* unwrapping. Phase 3 retro §2 last paragraph called this out explicitly:

> If Phase 4 or later wants to add another field to the AAD (e.g. `client_id`, `aud`), it has to either be in the request context (header, body) or in the wire prefix.

Phase 4 added `appId` to the preamble (`peekSealedTokenAppId`) so the routes can resolve `Storage.getAppByClientId` → derive sealing key → unwrap with the matching AAD. Final wire format is now `version || appIdLen || appId || userKeyLen || userKey || iv || ciphertext || tag`. AAD remains `appId || userKey || version` (unchanged from Phase 3).

### Why the plaintext leak is OK (the second time)

The plaintext-leak argument is the same as Phase 3 §2 for `userKey`: `appId` (= `client_id`) is not a secret. It's the OIDC `aud` claim, it's in `/.well-known/openid-configuration` registrant docs, and it shows up on every front-channel handshake. The leak buys body-less unwrap.

`unwrapSealedToken` now takes `expectedAppId` and rejects mismatch *before* AAD verification (`src/oidc/sealed-token.ts:68`). The plaintext payload's `appId` field is *also* checked post-decrypt (`src/oidc/sealed-token.ts:143`) — defense in depth: a tampered preamble is caught at the AAD layer, a swapped ciphertext is caught at the JSON layer.

### Future signal

The wire preamble now carries `(version, appId, userKey)`. If Phase 5+ ever wants to add a fourth field, the same gate applies: must be non-secret AND must be needed for body-less unwrap. Don't pile fields in for convenience.

## 2. RFC 7009 §2.1 forced a refactor at the end of the phase

### Symptom

Initial `/oidc/revoke` implementation gated the upstream Toss `accessRemove` call on `token_type_hint === 'refresh_token'`. A pass-1 review caught this: RFC 7009 §2.1 RECOMMENDS that the server invalidate across token types when the hint is wrong or absent. The sealed wrapper carries `userKey`, which is what `accessRemove` actually consumes — gating on the hint loses information the server already has.

### Fix

Final commit on the branch (`refactor(oidc): revoke calls accessRemove on every unwrap`): drop the hint gate, always call `accessRemove(userKey)` on successful unwrap, surface the result in the audit log as `access_remove_ok: boolean` so operators can tell from the log whether Toss actually invalidated upstream. The hint stays in the request schema (clients still send it) but doesn't affect server behavior.

### Lesson

When implementing an RFC, read the SHOULD/RECOMMENDED clauses in §2 even when MUST clauses look complete. RFC 7009's MUST is "always 200" (locked early in the phase); the SHOULD is "search across types when hint mismatches" (missed until review). Phase 5+ when implementing real Toss endpoints will hit similar ambiguities — re-read the full §2 of every RFC before declaring an endpoint done.

### Carryover

Audit detail shape `{ access_remove_ok: boolean }` is now a public contract for `oidc.token.revoke`. Phase 5's real Toss adapter must preserve it (don't lose the boolean when swapping mock for real adapter).

## 3. Auth-method ambiguity rejection landed in code, not just tests

### What happened

Phase 3 retro §7 carryover #7 said:

> Lock down "mixing public Origin + confidential `client_secret` on the same call → reject" with explicit tests (plan Task 12). The lesson from M1 was that auth-method ambiguity is exploitable.

Phase 4 implemented the rejection in `src/oidc/client-auth.ts` as a **resolver** that returns one of `{ method: 'basic' | 'post' | 'public', clientId, … }` or throws `invalid_client`. The mixing-rejection test (`token-route.test.ts`) covers four cases: basic+post both present, basic+Origin both present, post+Origin both present, wrong-secret-with-Origin (must NOT fall through to public). The last one was added in the same pass-1 review pass as §2 above — it locks the no-fallback invariant in code, not just docs.

### Why "no fallback to public when confidential auth fails"

A client that registered a `client_secret` is confidential. If the call presents that `client_secret` (correctly or not) AND a valid `Origin`, falling through to public on bad secret would let an attacker who controls the browser bypass the secret check. The resolver throws `invalid_client` instead.

Phase 5+ (real Toss + real consumer apps) inherits this invariant. New auth methods (mTLS-bound JWT? `private_key_jwt`?) added in later phases must integrate as additional discriminated branches in the same resolver, not as parallel checks elsewhere.

## 4. Origin allowlist hardening (small, but easy to miss)

`src/oidc/origin-check.ts` got tightened to reject `null`, whitespace-only, and trim-mismatch values, plus an empty allow-list (which previously implicitly accepted any Origin). 10-line change but it's the difference between "Origin auth is real" and "Origin auth is theatre." Phase 3 plan Task 11 had pencilled this in; Phase 4 actually shipped it.

Test added in `origin-check.test.ts`. Discovery test (`discovery-route.test.ts`) and origin-check test got 2 lines each to assert the new behavior — quiet but load-bearing.

## 5. `accessRemove` signature changed mid-phase

### Symptom

Initial implementation took `accessRemove(refreshToken: string)`. Plan §6.3 actually specifies `accessRemove(userKey: string)` — the upstream Toss endpoint is called with `userKey` from `/login-me`, not the refresh token. A `fix(toss)` commit early in the phase flipped the signature.

### Why it matters

The mock adapter's counter pattern (Phase 3 retro §3) keys on the input arg. Switching from RT to userKey changed what the test asserts. Phase 4 happened to catch this before any consumer baked in the wrong call shape. Phase 5's real adapter will be checked against the same plan §6.3, but if the real Toss endpoint actually takes RT (despite plan), Phase 5 needs to flip the contract back.

### Future signal

When the real adapter lands in Phase 5, regenerate the redacted fixture for `/access-remove` and verify the request body matches `userKey`, not RT. Don't trust the plan blindly — Phase 5's first integration test should be a fixture-vs-real diff.

Phase 0 redact list covered `client_secret`, `refresh_token`, `code`, `access_token`, `id_token`, `code_verifier`, `mtls_*`. Phase 4 plan Task 17 said "verify, do not extend." After implementation the audit revealed two genuine gaps: `req.headers.authorization` / `res.headers.authorization` (bearers in HTTP layer), and the top-level `token` form field on `/oidc/revoke` (RFC 7009 calls the field `token`, not `access_token` or `refresh_token`).

Single commit `chore(log): redact authorization headers + token form field` extended Pino's redact list with exactly those two paths — no speculative additions. Phase 8 (observability) will revisit when structured logs are codified end-to-end.

## 8. Carryover for Phase 5

1. **`MockTossAdapter` → real `TossAdapter`** with the same interface: `generateToken`, `refreshToken`, `loginMe`, `accessRemove(userKey)`. Counter-style assertions in tests (Phase 3 §3) get replaced with fixture-driven contract tests; mTLS handshake gets gated behind `pnpm test:e2e:live`.
2. **mTLS material is per-app**, sealed in `apps.mtls_cert_sealed` / `mtls_key_sealed` (Phase 2). Phase 5 fetches it via `Storage.getAppByClientId` + `unwrapMtlsBundle` (new helper, not yet written). The sealing info is `'ait/mtls/v1'` (distinct from token sealing `'ait/seal/v1'`) — token-cipher leak can't decrypt mTLS material.
3. **Sandbox cert provisioning** is the dog-food blocker: console UI generates the cert, but the CLI-side `aitcc app certs issue` does not exist yet. That's tracked in umbrella TODO Phase 4.5 and a parallel console-cli worktree (`feat/aitcc-app-certs-issue-revoke`). Phase 5's worker should not block on it — sandbox cert can be generated by hand once for the first run, and CLI-issue is the cleanup pass.
4. **Toss envelope** (`{ resultType, success?, error? }`) handling lives in `src/toss/envelope.ts` (Phase 3 §3). Phase 5's real adapter goes through it; new error codes from real Toss get mapped at the envelope boundary, not at the adapter call site.
5. **Audit `access_remove_ok: boolean`** stays in the contract (§2). Phase 5 must preserve it after the adapter swap.
6. **`peekSealedTokenAppId`** is now part of the public surface for any future bearer-driven endpoint. Don't bypass it.
7. **Origin allowlist hardening** (§4) is in main; Phase 5 doesn't touch this.
8. **Confidential-client resolver** (§3) is in main and load-bearing for any future auth method; new methods extend the discriminated union rather than parallel checks.
