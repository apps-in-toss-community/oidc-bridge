## 1. Plan-vs-main mismatch: `service.apps.getMtlsMaterial` did not exist

### What happened

Phase 5's plan (lines 73, 7) names `service.apps.getMtlsMaterial(appId)` as a Phase 2 deliverable that the new adapter should consume. It does not exist on `main` — `src/apps/service.ts` exposes CRUD for apps but no decryption helper that returns plaintext PEMs. Phase 2 stored `mtls_cert_enc` / `mtls_key_enc` as encrypted columns and (correctly) never exposed plaintext through the admin REST surface; nothing else in Phases 0–4 needed plaintext.

### Fix

Added `createMtlsMaterialAccessor` in `src/server.ts` (commit `70c84e8`). It threads `storage.getApp` + `masterKeyProvider.getKeyBytes` + `deriveSealingKey` + `decryptColumn` together and returns a `(appId) => Promise<{certPem, keyPem} | null>` matching the `RealTossAdapterDeps.getMtlsMaterial` signature. Tested in `src/server.test.ts` with an `encryptColumn → decryptColumn` round-trip. Adapter is purely interface-driven (a function), so the *implementation* belongs at the bootstrap layer that owns the master-key provider, not in `apps/service.ts`.

### Lesson

The plan was written assuming a Phase 2 deliverable that Phase 2 didn't ship. That's fine — Phase 2 didn't need plaintext, and the plan's job is to describe the destination, not to retroactively prove every prerequisite landed. **When a plan names an accessor that doesn't exist, build it where the dependencies already live (= bootstrap), not where the plan suggests** — `service.apps` doesn't have the master-key provider, so adding the accessor there would have meant either passing the provider through or leaking sealing-key derivation into the apps layer. Both worse than a 19-line factory at the bootstrap seam.

### Carryover

`createMtlsMaterialAccessor` is now the only place that turns sealed `mtls_cert_enc` / `mtls_key_enc` columns into plaintext. Phase 6+ should not re-implement this; if a second consumer appears (admin "test cert" tool, doctor command), share this accessor.

## 2. ESM bindings on `node:tls` are immutable — the spy didn't fit

### Symptom

Plan Task 8 ("Indirect mTLS verification") asks for a test that proves cert+key bytes reach `tls.createSecureContext`. The natural shape is `vi.spyOn(tls, 'createSecureContext').mockImplementation(...)` so the test can read back the options. Vitest fails with `TypeError: Cannot redefine property: createSecureContext` — Node's ESM `node:tls` namespace is a frozen module record.

### Fix

Replaced the spy with a *capture* pattern at the layer the adapter exposes anyway: `RealTossAdapterDeps.buildDispatcher` is a function the adapter passes the cert+key into. The test supplies a custom `buildDispatcher` that records `{certPem, keyPem}` to an outer object and returns a no-op dispatcher. Combined with Task 7's "default builder returns a real `undici.Pool`" assertion, this is the same proof: the real builder routes cert+key into `undici`'s `connect: { cert, key }`, which `undici` hands to `tls.createSecureContext`. The seam shifts from `tls` itself to `undici`'s contract with `tls`, but we own that seam.

The test file (`src/toss/real-adapter.test.ts:224-256`) carries an inline comment explaining why the obvious spy doesn't work, so future reviewers don't try the same thing.

### Lesson

ESM module mocking has hard ceilings the docs don't always advertise. **When `vi.spyOn` fails on a `node:*` import, redesign the test to capture at a contract you own**, not the platform module. The DI seam already existed in the adapter constructor (`buildDispatcher`); we just hadn't been routing the test through it.

### Carryover

The DI pattern (`buildDispatcher?: (opts) => unknown`) is now load-bearing for Phase 8+ when we add metrics around the dispatcher (latency timer, retry counter): wrap the default builder, don't reach for `tls`. Phase 6 doesn't touch this.

## 3. Per-`appId` dispatcher cache — invariants + future eviction

### Decision

`RealTossAdapter` keeps `private readonly dispatchers = new Map<string, unknown>()`. First call for a given `appId` builds the dispatcher (via `getMtlsMaterial` → `buildDispatcher`) and caches it; subsequent calls reuse. This amortizes TLS handshake cost across requests for the same tenant in a long-running server.

### Invariants the cache assumes (and is allowed to assume)

1. **mTLS material is immutable per appId in process lifetime.** If an operator rotates an app's cert+key, the running bridge keeps using the old dispatcher until restart. This is acceptable because cert rotation is a manual ops action that operators can pair with `docker compose up -d` (or a SIGHUP handler later); it's not a frequent enough event to justify a cache-invalidation API in Phase 5.
2. **No TTL.** A bridge that never restarts and has hundreds of apps could grow the map without bound. In practice the public instance is sized for a small number of tenants, and self-host is single-app. Phase 8 (rate-limit, observability) is the natural place to add `LRU(maxApps)` if the public instance ever needs it.
3. **Cache is keyed only on `appId`, not on `(appId, masterKeyVersion)`.** Master-key rotation (Phase 1's contract) does *not* invalidate the dispatcher, because the dispatcher only cares about mTLS PEMs, which are decrypted inside `getMtlsMaterial` once per app. The sealing-key-version hop happens before the cache, so the cache stays correct under rotation.

### What the unit test actually pins

`src/toss/real-adapter.test.ts:6-31`: three calls — `app_a`, `app_a`, `app_b` — produce exactly **two** `buildDispatcher` invocations. That's the entire load-bearing assertion; nothing else about cache shape or eviction is contractual.

### Carryover

Phase 8 may add a "drain dispatcher on app delete" hook when the admin DELETE app flow is reviewed for resource cleanup. Today, deleting an app does not close the cached `Pool` — orphan dispatchers GC when the bridge restarts. Acceptable for now; track it explicitly if the public instance ever supports app deletion at scale.

## 5. Things Phase 6+ should not re-litigate

- **Toss AT signature is not validated.** The CLAUDE.md statement ("Bridge treats it as opaque, claims come from `/login-me`") is now load-bearing in `loginMe`'s implementation: we never look at the AT's JWT body. Don't add JWKS-fetching code "just in case."
- **`accessRemove` does not surface a `boolean` from the upstream.** Phase 4 retro §2 says `audit.detail.access_remove_ok: boolean` is a public contract; the real adapter resolves to `void` on SUCCESS and throws `TossUpstreamError` on FAIL. The route layer is what writes `access_remove_ok = (try { await accessRemove } catch { false })`. Don't push the boolean into the adapter signature.
- **Five `.real.json` placeholders are `{}` for now.** They land empty deliberately — fixture capture requires a sandbox cert that isn't in this session. Phase 6+ session that *does* have the cert should run `pnpm spike:toss` and amend in a separate doc-only PR.
