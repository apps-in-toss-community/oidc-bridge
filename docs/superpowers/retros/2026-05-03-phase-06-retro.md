## Goal vs. shipped

Goal: wire the `user_sessions` table (added in Phase 1's schema) plus stub
`POST /admin/login` + `POST /admin/logout` behind a
`BRIDGE_ENABLE_SESSION_LOGIN=1` feature flag. Forward-compat scaffolding for
a future multi-user web console — **not** a user-visible feature this
release. Default behavior unchanged.

Shipped: all of the above plus a `users.password_hash` column, a
`setUserPassword` storage method, an offline `oidc-bridge user set-password`
CLI, a startup task that purges expired sessions on boot, and a logger
redact-list extension covering `password_hash` and Set-Cookie headers. 11
small commits, 305 tests pass (1 skipped — pg conformance gated by
`PG_TEST_URL`).

The bootstrap entrypoint (`server.ts`) does **not** wire the session block
yet. The flag alone is currently a no-op until `main()` constructs
`createApp({ session: { service } })` from the flag. That's intentional for
this phase — invisible-by-default — but it means turning the flag on in prod
today does nothing observable. Phase 7 (or a tiny follow-up) will close
that.

## Plan-vs-shipping mismatches (for next phase's planner)

The plan was written against an idealized repo shape that didn't match
reality. Adapted on-the-fly:

1. **Migrations**: plan assumed hand-written SQL files in
   `migrations/{pg,sqlite}/`. Repo uses **drizzle-kit auto-generated**
   migrations under `drizzle/{pg,sqlite}/`. Used `pnpm db:generate:pg` /
   `db:generate:sqlite` after schema edits; resulting files
   (`0001_jazzy_naoko.sql`, `0001_sharp_the_fury.sql`) are committed
   verbatim from drizzle-kit.

2. **Storage API surface**: plan assumed `Storage.exec(sql, params)` and
   `Storage.query(sql, params)` raw escapes. Neither exists — Storage is
   strictly typed Drizzle methods. Solved by **extending the interface**:
   added `setUserPassword`, `deleteUserSessionsByUser`,
   `purgeExpiredUserSessions`. Both pg + sqlite implement; conformance
   covers both.

3. **Index already existed**: plan added a "create
   `user_sessions(user_id)` index" task. The index was already declared in
   Phase 1's schema as `user_sessions_user_idx`. Replaced the migration
   with a conformance-style assertion in `migrate.test.ts` to pin its
   continued existence.

4. **`BridgeConfig` loader**: plan referenced one. There isn't one — the
   repo uses focused per-section loaders (`loadOidcConfig`,
   `loadTossConfig`). Added `loadBridgeFlags` in the same file as a third
   section.

5. **`sid` vs `id` column**: plan called the session primary key `sid`. The
   actual schema column is `id`. Used `id` consistently throughout the
   `sessions/` module — type lives in `Session.id`, store calls use
   `getUserSession(id)`, etc.

6. **CLI offline pattern**: plan suggested `BRIDGE_DB_URL=sqlite://...`
   env. Repo's existing CLI commands all use `--db-path <path>`
   (see `cli/commands/_shared.ts`). Followed the existing pattern;
   `set-password` ships as offline-sqlite-only with `--db-path` +
   `--password` (or stdin).

7. **Bcrypt timing-equalizer hash**: plan provided a literal hash string
   that wasn't a valid bcrypt format (period in salt, wrong length).
   bcryptjs would throw on `compare`. Replaced with `bcrypt.hashSync(...)`
   computed once at module load — small startup cost (~5 ms), no chance of
   silent breakage.

For Phase 7's planner: do a quick `Read` pass over the actual repo modules
the plan references (Storage interface, CLI shared options, config
loaders, drizzle output dir) before fixing concrete API shapes. The plan
read like a coherent design but several leaf details didn't match the
codebase Phase 5 left behind.

## `__Host-bridge_session` cookie decisions

- **`__Host-` prefix** (RFC 6265bis): blocks subdomain takeover, requires
  `Path=/` + `Secure` + no `Domain` attribute. Implies the cookie cannot
  be sent over plain HTTP — so session login does not work on a self-host
  setup that exposes the bridge as `http://localhost:8080`. Documented in
  RUNBOOK.
- **`SameSite=Lax`** (not `Strict`): admin console SPAs typically live on
  the same origin or a sibling, but operators may bookmark
  `/admin/dashboard` and follow links. Lax keeps top-level navigation
  flows working without re-login while still blocking cross-site POST.
- **No `Max-Age` on `setSessionCookie`** — uses `Expires` derived from
  `session.expiresAt` so the browser-side cookie expiry tracks the
  server-side session expiry exactly. `clearSessionCookie` uses
  `Max-Age=0` (the universal logout idiom).
- **`HttpOnly`**: hardcoded; no opt-out. The cookie value is a server-side
  session id — JS never needs to read it.

## Flag-gate edge cases

The flag is enforced **at mount time**, not at request time. That means:

- Flag off → `app.route('/', mountSessionRoute(...))` is never called →
  Hono returns 404 for both `/admin/login` and `/admin/logout`,
  indistinguishable from "endpoint does not exist." This is the strongest
  default-off the framework supports.
- Flag on **but** `session.service` not supplied → still 404 (the `if
  (opts.session)` guard short-circuits). This means `server.ts` must do
  the wiring separately. Currently `server.ts` doesn't construct the
  session block at all — it'd be a 4-line addition (read flag → if true,
  build `createSessionService` from `createSessionStore(storage)` → pass
  to `createApp`). Deferred to keep this phase invisible-by-default.

The `setUserPassword` CLI works **regardless** of the flag — passwords
can be pre-seeded so a future flag flip is one restart away.

## What was deliberately not done

Per the brief's "don't do" list:

- No CSRF token on `/admin/login` — we accept that the flag-on surface
  needs CSRF before becoming a real console. Out of scope for placeholder.
- No rate limit on `/admin/login` — Phase 8's sliding-window in-memory
  rate limit will cover this.
- No "remember me" — session TTL is set by caller (`createSessionService`
  takes `ttlMs`), no UI hook.
- No session validation middleware on existing admin routes — admin REST
  stays API_TOKEN-only. Adding session bearer auth to `/admin/workspaces`
  etc. would change Phase 2's invariant.

## Carried into Phase 7

- `server.ts` wiring of the flag → service → `createApp` block (4 lines).
- A real `aitcc-bridge user create` CLI (currently users only exist via
  the bootstrap path; `set-password` requires a pre-existing row).
- Periodic session purge (right now only on startup). Either a tiny
  in-process timer or `POST /admin/sessions/purge` for external cron.

These don't block Phase 7's CLI bootstrap/doctor work — they're loose
follow-ups.

## Sub-agent delegation observations

I worked the whole phase inline rather than delegating. In retrospect:

- **Mirror tasks** (sqlite ↔ pg `setUserPassword` impl) would have been
  straightforward haiku delegations — the second implementation is an
  exact structural mirror of the first. Cost in attention/context probably
  wasn't worth the round-trip for a 6-line method, but for a multi-method
  storage extension it would be.
- **Independent test authoring** for the cookie helpers (6 tests, no
  cross-cutting concerns) could have been a parallel sonnet call while I
  worked on the service.
- **Drafting this retro** — could have been an opus call after a "here's
  what shipped, here's what mismatched" briefing. I wrote it inline
  because I had the full context fresh.

For Phase 7, plan ahead: identify mirror tasks (sqlite↔pg, route-pair
endpoints) early and queue them as parallel haiku/sonnet calls.
