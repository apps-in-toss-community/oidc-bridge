## Goal vs. shipped

Goal: ship two operator commands that take a fresh machine to a working,
verifiable bridge install. `oidc-bridge bootstrap` writes a sqlite DB +
master-key file + first user + first workspace + first admin API token
in one offline call; `oidc-bridge doctor` runs five probes (env / db /
master-key / jwks / toss) and emits a green/yellow/red report with a
TTY-colored or JSON view.

Shipped: both commands, ten new files under `cli/`, an end-to-end test
that bootstraps a tmp dir and asserts doctor lands green-or-yellow,
SELF_HOSTING.md walkthrough, and a RUNBOOK pointer to it. 11 small
commits, lint + typecheck + full test suite green on every commit.

The Toss probe sends a placeholder access token and accepts a
`Toss FAIL` envelope as **green** (it proves mTLS handshake worked); a
network/TLS failure is red. This means doctor needs only the cert + key
to give a meaningful answer — not a fresh `authorizationCode`.

## Plan-vs-shipping mismatches (continuing the Phase 6 list)

The plan had the same idealized-vs-real-repo gap Phase 6 flagged. The
upfront `Read` pass over Storage interface, ids.ts, secrets.ts, master
keys, real-adapter, config.ts caught most before I wrote a single line.
The mismatches:

1. **CLI flag names**: plan used `--db <url>` (with sqlite/pg URL
   parsing). Repo's existing CLI uses `--db-path <path>` (sqlite-only,
   plain filesystem). Followed the existing pattern.

2. **Token / id prefixes**: plan invented `bait_*` for API tokens and
   `u_*` for user ids. Real prefixes from `src/ids.ts` are `tok_*`,
   `user_*`, `ws_*`, `app_*`, `mk_*`, `ses_*`, `au_*`. The bootstrap
   summary surfaces these so the operator pastes them straight into env.

3. **Storage API**: same Phase 6 finding — Storage is typed Drizzle
   methods, no raw `query/exec`. Bootstrap composes `createUser`,
   `createMasterKey`, then the apps-service for workspace + token (so
   audit log entries are written and the same `tok_*` generator runs).

4. **API token issuance**: plan assumed bootstrap minted a token
   directly. Real path is `service.apiTokens.create(ctx, { name,
   scopes })` returning `{ token, plaintext }`. Used the service to
   keep the audit-log invariant and avoid forking the token format.

5. **MasterKeyProvider env hook**: plan's master-key probe took an
   `env: ProcessEnv`-style override. Real `createEnvMasterKeyProvider`
   reads `process.env` directly with no override. Solved by saving the
   relevant keys, mutating `process.env` for the duration of the probe,
   and restoring in `finally` — confined to the probe; production
   doesn't go through that code path.

6. **Toss `FAIL` detection**: plan suggested introspecting on
   `EnvelopeError` shape. Real `mapEnvelopeError` rolls everything into
   a `TossUpstreamError` with code `invalid_grant` (for INVALID_TOKEN-
   class) or `upstream_error` (otherwise) and preserves the literal
   `Toss FAIL: <CODE>: <message>` substring in the message. Probe uses
   that substring as the disambiguator — no need to peek into the
   envelope object.

7. **`OIDC_SIGNING_KEYS` shape**: plan referenced a JSON-blob env. Real
   convention (from `src/config.ts`) is one env per kid:
   `OIDC_SIGNING_KEY_<KID>_PEM` (uppercase in env, lowercased internally).
   Doctor's `collectSigningKeysFromEnv` mirrors that loader.

8. **`SQLITE_PATH` default**: plan didn't specify a fallback. Server
   defaults to `./data/oidc-bridge.sqlite` if the env is unset, so the
   doctor command falls back to the same path — keeps "doctor with no
   args after bootstrap with default `--db-path ./data/oidc-bridge.sqlite`"
   working out of the box.

9. **RUNBOOK first-time setup**: plan said "replace the first-time setup
   section". RUNBOOK had no such section — it's purely operational. Added
   a top-of-doc pointer to SELF_HOSTING.md instead of carving up the
   existing structure.

For Phase 8's planner: the same upfront-Read discipline is the cure.
Don't trust plan-text for repo-shape claims older than two phases.

## Bootstrap idempotency: refuse, don't overwrite

The plan implied a `--force` flag for re-bootstrapping. I shipped it
without one. The reasoning:

- Re-bootstrapping into the same master-key dir would overwrite `v1.key`,
  silently making **every sealed token in the wild and every sealed
  mTLS PEM in the DB unrecoverable**.
- A tired operator at 2 AM running "let me just try `--force`" is the
  exact failure mode this command must not enable.
- Recovery from accidental re-bootstrap requires `rm -rf` of both the
  DB and the master-key dir, which is a deliberate-enough action that
  having it as the only path is fine.

Bootstrap therefore checks two things and refuses on either:

1. `<master-key-dir>/v1.key` already exists.
2. The DB already has a `users` row matching `--email`, **or** the
   `master_keys` table has a v1 row.

The check ordering means a missing/empty DB + missing key file is the
only "first run" success path, which matches operator intuition.

## JWKS roundtrip: PKCS#8 → derived SPKI → jose

The jwks probe needs the public counterpart of the private signing key
to verify what it just signed. The repo doesn't store the public PEM
separately — it's derived from JWKS at runtime. The probe replicates
that derivation:

```
PKCS#8 PEM
  → node:crypto.createPublicKey(privPem)
    → .export({ type: 'spki', format: 'pem' })
      → jose.importSPKI(spki, 'RS256')
```

This is the exact same path `/.well-known/jwks.json` takes (via
jose.exportJWK), so a green probe means a real consumer's JWKS fetch
will round-trip too. If we ever switch to EC keys we need to widen the
import alg list, but RS256 is locked in for the public instance.

## Probe shape lifts cleanly to Phase 8 `/status`

Each probe returns `{ name, state: 'green'|'yellow'|'red', detail:
string }`, and `runDoctor` aggregates to `{ status, items }` with
worst-state precedence. That same shape is what Phase 8's `/status`
HTML page wants — five colored boxes + detail strings.

What's reusable:

- The probe functions themselves (`runEnvProbe`, `runDbProbe`,
  `runMasterKeyProbe`, `runJwksProbe`, `runTossProbe`).
- `runDoctor`'s aggregation.
- The TTY-vs-JSON discriminator in `cli/output.ts` is *not* reusable —
  `/status` will be HTML — but the JSON branch is.

What's *not* reusable as-is: the doctor command runs probes serially
and exits the process. `/status` will run them on a per-request basis
(or with a short cache) and respond with JSON. Phase 8 should refactor
the orchestrator into "evaluate → ProbeReport" + "render" — already
half-done since `runDoctor` is decoupled from `cli/output.ts`.

The toss probe in particular wants a per-request cache (5–30 s) before
mounting on `/status`: it does a real outbound TLS handshake every
time. A burst of `/status` hits would Toss-flood for nothing.

## What was deliberately not done

Per the brief's "don't do" list:

- **No probe plugin abstraction.** Five probes is a manageable list;
  premature plugin systems get in the way. If Phase 8 needs runtime
  probe registration we add it then.
- **No `bootstrap --force`.** See above.
- **No PG bootstrap.** Self-host first-class is sqlite + file. PG is
  the public-instance shape (Phase 10), provisioned out-of-band.
- **No raw Toss-token exposure in doctor**. The probe's adapter is
  scoped to a single `loginMe` call with a placeholder AT — even on
  green, the FAIL envelope or success body is summarized into a
  detail string, never echoed verbatim.
- **No new prod deps.** `bcryptjs`, `jose`, `commander`, and the rest
  were already in. The CLI imports a bit more of `node:crypto` than
  before but stays in stdlib.

## Sub-agent delegation observations

I worked the whole phase inline again. The reflection from Phase 6 said
"identify mirror tasks early and queue them as parallel haiku/sonnet
calls" — this phase had fewer of those:

- The five probe files are siblings but not mirrors; each one's logic
  diverges meaningfully (env validates strings, db touches storage,
  master-key forks on provider type, jwks does crypto, toss does
  network). Parallel sonnet calls would have been viable but I kept
  them inline because each one needed me to look up real APIs.
- The TTY reporter was a self-contained ~70-line module — a sonnet
  delegation would have been fine. Inlined for context-keeping.
- This retro could have been an opus call given a "here's what shipped"
  briefing. Wrote it inline because the context was fresh.

What I'd actually farm out next phase: **doc generation**. SELF_HOSTING.md
is a structured walkthrough that follows a known pattern; a sonnet call
with the bootstrap summary block and the probe table as input could
have produced a first draft I'd then edit. ~5 minutes saved.
