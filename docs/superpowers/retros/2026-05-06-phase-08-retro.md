## Plan-vs-shipping mismatches

The plan was accurate on API shapes — Phase 7's retro discipline of
reading real module surfaces before writing code paid off here. The
mismatches that did surface were mechanical rather than architectural:

1. **Body-cache API**: the plan proposed writing back to a hypothetical
   `c.req.bodyCache.text` field to allow downstream handlers to re-read a
   body already consumed by the rate-limit middleware. Hono's actual
   internal body-cache field is `bodyCache.formData` and `bodyCache.json`
   (not `.text`). The solution: the middleware pre-reads the body, writes
   into both typed cache slots directly, and `parseBody()` / `json()` in
   downstream handlers skip the re-parse. Mentioned in the PR implementation
   notes as a reason for the non-obvious field writes.

2. **`c.req.bodyCache` visibility**: `bodyCache` is typed as a private
   field in Hono's `HonoRequest`. The rate-limit middleware had to cast it
   with `as` to reach the cache slots. This is fragile against Hono version
   bumps — added a comment in `rate-limit-route.ts` calling out the version
   dependency.

3. **`IP_HASH_SALT` default per-process**: the plan specified `randomBytes(16)`
   as the default. `node:crypto.randomBytes` is synchronous and fine for
   a one-time call at module load. In practice the salt was generated at
   `config.ts` load time (startup), not at the first request, which matches
   the intent but meant the test for "random per process" required a test
   process restart to observe distinct values. Documented in comments, not
   in tests.

4. **OTel dynamic import string cast**: TypeScript's module resolver tries
   to locate optional packages at typecheck time even inside `import()`
   expressions. The fix (`await import('@opentelemetry/sdk-node' as string)`)
   is noted in the PR body as the mechanism — the `as string` defeats
   static analysis so the type checker doesn't fail on missing optional deps.
   This pattern is not well-documented outside TS issues; worth preserving
   as tribal knowledge.

5. **`/status` Toss probe omission**: the plan explicitly said "no Toss
   probe on `/status`" (mTLS handshake cost per status hit). Shipped as
   specified. The `/status` probe set is `db`, `master-key`, `jwks`,
   `last-healthz` — four items, not five. The plan's runtime probe spec
   matched the shipped set, so this was a non-issue; recorded here for the
   reader who expects parity with doctor's five probes.

## Middleware ordering: the non-obvious constraint

The plan listed middleware order as: `requestId → pinoHttp → rateLimit →
routes`. The constraint that makes this order mandatory (not merely
conventional):

- `requestId` must precede `pinoHttp` so the log line carries the request
  id. Reversed order means the log line has `request_id: undefined`.
- `pinoHttp` must precede `rateLimit` so **429 responses get a log line
  too** — otherwise rate-limited requests are invisible in logs.
- `/healthz` and `/status` must be registered **before** `rateLimit` is
  mounted. Both are operator probes that need to stay reachable under load.
  A misconfigured mount (rate-limit before health endpoints) would make
  `/healthz` fail under its own traffic, which is the worst failure mode
  for a load-balancer health check.

Hono processes middleware in registration order; the mount-point ordering
in `src/app.ts` enforces all three constraints implicitly.

## Sliding-window algorithm: Cloudflare-style weighted blend

The plan specified a "single-bucket approximation" without naming an
algorithm. The shipped implementation is the same Cloudflare sliding-log
approximation described in their blog:

```
effective = previous_count * (1 - intoWindow) + current_count
```

where `intoWindow = (now - windowStart) / windowMs` is the fraction of
the current bucket elapsed. This gives a smooth decay from the previous
window's count rather than a step reset. Compared to strict fixed-window
counting it prevents the "burst at window boundary" attack where a client
sends `2 × limit` requests in a 2-second span straddling a window reset.

The eviction sweep (`maybeSweep` every 1000 ops, deletes entries with
`windowStart < now - 2 * windowMs`) keeps the in-memory map bounded in
long-running deployments. The test for eviction confirms `size() < 1000`
after 1000 keys age out — conservative but sufficient for a correctness
check. Memory usage scales with unique active keys per window, not
request volume.

Multi-replica deployments share no rate-limit state. Each instance has
its own counters. This is the documented "self-host simplicity" trade —
the public cloud instance runs behind a Cloudflare Workers layer with its
own rate limiting (Phase 12c), so the Node-side limit is a secondary
backstop, not the primary enforcement point.

## OTel lazy-import pattern

The `'@opentelemetry/sdk-node' as string` cast is a documented TypeScript
trick for truly optional dynamic imports. Without `as string`, `tsc` still
tries to resolve the module at compile time and fails if `optionalDependencies`
are absent. With `as string`, the import becomes opaque to the type checker
— the cost is that the call site loses the return type, requiring an
explicit cast or `// @ts-ignore`.

The shipped approach casts the resolved module's type manually:

```ts
const { NodeSDK } = await import('@opentelemetry/sdk-node' as string) as typeof import('@opentelemetry/sdk-node');
```

This preserves IDE autocompletion for the installed case while staying
silent when the package is absent. The `as string` form is stable — it's
not a Hono or TS version-specific quirk, just a type-system escape hatch.

## What was deliberately not done

Per the plan's "don't do" list (confirmed not shipped):

- **No metric registry abstraction**: only what OTel auto-instrumentations
  provide. No custom `Counter`/`Histogram` registrations.
- **No rate-limit storage backend**: in-memory only. No Redis, no shared
  external counter. Documented in RUNBOOK.
- **No Toss probe in `/status`**: see above. Doctor's Toss probe is
  intentionally absent from the runtime status page.
- **No raw IP in logs**: IPs are sha256-hashed with `IP_HASH_SALT`. The
  raw IP is never written to any log field, even in debug mode.
- **No body logging**: `pinoHttp` logs method, path, status, latency,
  user-agent, ip_hash — not the request body. The test for "does not log
  the request body" in `pino-http.test.ts` is the lint on this invariant.
- **No new prod deps beyond OTel (optional)**: pino and pino-http-style
  logging are hand-rolled without the `pino-http` package; `node:crypto`
  covers randomUUID and sha256. No new required runtime dependencies added.

## `/status` as an incident aid

The design decision to make `/status` unauthenticated and no-cache is
worth recording explicitly:

- **Unauthenticated**: an operator who has lost API token access (DB
  unreachable, master key missing) still needs to see the bridge's self-
  assessment. If the status page required a bearer token, it would be 401
  during the exact incident it's meant to help debug.
- **`cache-control: no-store`**: load balancers, CDNs, and browsers must
  not cache the status page. A stale "green" from five minutes ago during
  an active incident is worse than no status page.
- **No Toss probe**: a Toss mTLS handshake on every `/status` request
  would impose a ~100 ms round-trip and a network dependency on every
  operator health check. Status probes that can fail for external reasons
  unrelated to the bridge's own health belong in the CLI doctor, not the
  runtime page.

## Probe set: runtime vs. doctor

The runtime status page and the CLI `doctor` command now have divergent
probe sets — intentionally:

| Probe | CLI doctor | `/status` |
|---|---|---|
| env | yes | no (already validated at startup) |
| db | yes | yes |
| master-key | yes | yes |
| jwks | yes | yes |
| last-healthz | no (stateful, process-local) | yes |
| toss | yes | no (mTLS cost per request) |

The `ProbeItem` shape (`{ name, state, detail }`) and the `worst-of`
aggregation are shared between the two surfaces — both use the same
`cli/output.ts` type and the same `runDbProbe` / `runMasterKeyProbe` /
`runJwksProbe` from Phase 7's doctor module.

## Carried into Phase 09c

Phase 8 completes the Node feature set. Phase 09c is the runtime
abstraction phase — WebCrypto ports, `Uint8Array` boundaries, D1 driver,
`runtime/node.ts` + `runtime/workers.ts` split. The middleware and
observability code added in Phase 8 is pure Node / Hono — no
crypto calls, no mTLS, no storage calls — so it should port cleanly
to the Workers entry with minimal adaptation. The rate-limit and
pinoHttp middleware use `node:crypto.randomUUID` and `node:crypto.createHash`
(sha256 for IP hashing); these are Web Crypto equivalents that exist in
Workers too, so the migration is a one-for-one import swap.
